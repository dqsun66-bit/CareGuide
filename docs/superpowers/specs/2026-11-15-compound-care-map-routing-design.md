# 复合就医与停车请求编排设计

## 问题

当前 `/chat` 对医院停车请求采用 `map_result or engine.process(...)` 短路。只要消息同时包含“医院”和“停车”，地图结果就会终止后续处理，导致同一消息中的症状分诊、挂号需求和行动约束丢失。高德医院文本搜索结果也未经院区级过滤，可能混入暂停营业地点、住院部、门诊楼和无关医院。

## 目标

- 纯停车请求继续使用确定性高德流程，不产生模型费用。
- 症状/挂号与停车并存时，主 Agent 和地图工具都执行并合并返回。
- 急症结果优先，急症时不继续查询停车场。
- 轮椅需求保留在地图选择结果中，并明确无障碍状态未经核实。
- 医院候选过滤停业点、楼宇型子 POI、无关医院，并合并明显的新院区别名。

## 设计

新增无模型的复合请求识别与结果合成模块。识别只依据明确症状、当前不适或挂号/就诊动作词，不让普通停车请求进入主 Agent。复合请求先执行主 Agent；若结果为急症则直接返回，否则再执行现有高德院区搜索，并把地图卡片附加到主 Agent 结果。

地图候选在保存前执行确定性过滤：去除停业名称；当用户没有明确查询具体楼宇时去除住院部、门诊楼、放疗中心等子 POI；对于“人民医院”等明确正式名称，仅保留名称相关项；合并同一医院的“新院区”别名。过滤不推断营业状态或无障碍能力。

## 验收

1. “我头疼，明天想去泰州市人民医院，坐轮椅，哪里停车方便？”同时返回分诊文本和地图院区卡片。
2. 上述请求只调用一次主 Agent，地图查询一次；纯停车请求不调用主 Agent。
3. 急症分诊不调用高德。
4. 候选中不出现暂停营业、住院部、门诊楼、放疗中心及无关医院。
5. 结果明确 `requires_wheelchair_access=true`，但不声称无障碍或实时余位已核实。
