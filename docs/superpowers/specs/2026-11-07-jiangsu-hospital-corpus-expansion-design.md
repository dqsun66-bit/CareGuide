# 江苏医院官方知识库核心内容扩展设计

## 1. 目标

在已经通过验收的 `jiangsu-hospitals-v1` 泰州试点基础上，为剩余12家江苏三级甲等医院补充每家3～5条高可信核心知识，形成独立的 `jiangsu-hospitals-v2`。

本阶段只建设经过官方来源核验的静态语料，不调用付费模型，不生成华为Embedding，不建立Chroma索引，也不接入AgentArts。完成后预计覆盖15家医院、45～69条正式知识记录，为下一阶段的华为向量化和重排序提供冻结输入。

## 2. 范围

### 2.1 医院范围

保留泰州3家试点医院的既有审核结果，并扩展以下12家医院：

- 南京：江苏省人民医院、南京鼓楼医院、南京市儿童医院、江苏省中医院
- 苏州：苏州大学附属第一医院、苏州大学附属第二医院、苏州大学附属儿童医院
- 无锡：无锡市人民医院、无锡市中医医院
- 常州：常州市第一人民医院
- 南通：南通大学附属医院
- 扬州：江苏省苏北人民医院

### 2.2 每家医院的内容范围

每家医院发布3～5条记录，优先顺序为：

1. 医院身份与三级甲等等级；
2. 主要院区和官方地址；
3. 官方预约方式；
4. 联系方式或就诊准备；
5. 报告查询、交通或其他有官方静态证据的便民信息。

如果没有可冻结、可核验的官方预约页面，允许使用联系方式或就诊准备替代，但必须建立预约资料缺口记录。实时号源、实时车位、实时路线、医生排班、诊断、处方和治疗建议不进入静态知识库。

## 3. 方案选择

采用“单一v2语料库、按城市分批扩展”的方案。相比一次性构建全部12家医院，该方案降低审核和回滚风险；相比每城市独立知识库，该方案避免后续Chroma和AgentArts增加多库路由复杂度。

实施批次固定为：

1. 南京4家；
2. 苏州3家；
3. 无锡2家；
4. 常州、南通、扬州各1家。

每批都必须完成来源冻结、独立审核、正文证据校验、专项测试和独立Git提交，上一批通过后才能进入下一批。

## 4. 数据架构

### 4.1 版本与目录

- `data/jiangsu_hospitals_v1/`：保持冻结，不覆盖；
- `data/jiangsu_hospital_sources_v2/`：保存12家新增医院的原始官方快照、来源清单和独立审核清单；
- `data/jiangsu_hospitals_v2/`：保存15家医院合并后的可发布语料；
- `data/eval/jiangsu_hospitals_v2/`：保存v2固定检索案例、SHA-256和BM25基线结果。

v2复制v1中已审核泰州记录时必须保持来源URL、快照字节、来源哈希、正文哈希和原审核信息不变。新增12家医院使用新的来源与审核记录。v2清单阶段明确标记为15家医院核心内容扩展版，不声明全国覆盖。

### 4.2 数据流

```text
官方医院/卫健委/政府/认可的官方预约页面
→ 原始页面冻结与SHA-256
→ needs_review来源登记
→ 独立审核清单
→ 逐事实证据校验
→ 清洗、去重、分块与元数据校验
→ 原子生成jiangsu-hospitals-v2
→ 固定BM25评测
```

构建时不得联网，不得自动抓取新页面，不得自行把 `needs_review` 升级为 `verified_official`。

## 5. 来源与审核边界

### 5.1 允许的来源

- 医院官方域名；
- 国家、省、市卫生健康主管部门；
- 政府网站；
- 已列入允许清单的官方预约平台，且只能证明预约类别事实。

搜索结果摘要、百科、营销平台、普通聚合挂号平台和无法确认发布主体的转载页不能直接作为正式证据。

### 5.2 冻结来源

每个来源必须记录：

- `source_id`；
- 医院和院区范围；
- 来源URL与来源层级；
- 内容类别；
- 采集时间与有效期；
- HTTP状态与内容类型；
- 快照相对路径；
- 快照SHA-256；
- 初始状态 `needs_review`。

### 5.3 独立审核清单

来源审核必须绑定 `source_id + snapshot_sha256 + reviewer + reviewed_at + decision`。正文审核必须绑定 `document_id + content_hash + source_ids + required_evidence_terms + reviewer + reviewed_at + decision`。

构建器只有在审核结论为 `approved`、审核时间不早于采集时间、快照和正文哈希完全匹配、证据词在绑定快照中存在时，才能发布记录。审核信息缺失、被拒绝或过期时构建失败。

别名、等级、院区、地址、预约方法和联系电话必须逐项有冻结证据。一个事实需要多个来源共同证明时，正文审核必须绑定全部来源，不能把跨来源推断伪装成单来源事实。

## 6. 缺失、冲突和时效

- 没有官方证据的类别不发布，并登记 `needs_review`；
- 两个官方来源冲突时，该字段状态为 `conflict`，在人工形成决策前禁止发布；
- 过期来源不能继续授权发布正文；
- 医院网站变更后必须重新冻结快照并重新审核，不能只更新哈希；
- 缺少预约页面时允许用联系方式或就诊准备替代，但不得暗示已经具备预约知识；
- 交通、停车和无障碍资料只有在官方静态页面可核实时才能发布，实时状态始终由外部工具处理。

## 7. 构建与回滚

v2构建器只读取冻结来源包和独立审核清单，验证完成后通过临时目录原子发布，不覆盖已有目标目录，不留下半成品。

每个城市批次使用独立提交。失败批次不得修改已经通过的冻结快照和审核清单。`jiangsu-hospitals-v1` 始终可作为回滚版本；v2全部通过前不切换CareGuide运行时检索入口。

## 8. 检索评测

v2建立不少于45个经过审核的BM25案例，并满足：

- 每家医院至少3个案例；
- 覆盖正式名称、已审核别名、院区/地址和预约或替代类别；
- 每家医院至少1个硬负例；
- 硬负例覆盖实时车位、实时路线、医生排班、诊断或治疗建议；
- 所有正例ID必须存在并属于声明的医院与类别；
- 案例文件SHA-256冻结在README；
- Recall@5不低于0.90；
- MRR不低于0.75；
- 硬负例准确率为1.00；
- 范围越界为0。

评测只使用现有 `BM25Index`，不生成自然语言回答，不调用模型或外部网络。指标说明必须明确范围预过滤和小语料规模对结果的影响，不能把高分描述成大规模向量检索能力。

## 9. 测试与验收

每个批次至少验证：

- 来源URL、主机、类别和来源层级边界；
- 快照存在、无链接/目录逃逸且哈希匹配；
- `reviewed_at >= collected_at`；
- 正文哈希和逐事实证据词；
- 医院、院区和来源范围一致；
- 无未审核别名、无重复正文、无过期和未决冲突；
- 构建过程零网络调用、零付费模型调用；
- 失败构建不留下目标目录；
- 无API密钥、Cookie、登录令牌和患者数据。

最终验收要求：

1. 15家医院均有3～5条可发布核心记录；
2. 所有发布记录都能追溯到冻结官方快照和独立审核结论；
3. 所有已知缺口、冲突和过期项均被显式阻止发布；
4. v2语料验证无错误、无重复、无未决冲突和过期来源；
5. 固定BM25评测达到既定阈值；
6. 专项测试和全量回归通过；
7. v1保持字节不变并继续可加载。

## 10. 非目标与后续阶段

本阶段不完成以下工作：

- 全国医院覆盖；
- 华为Embedding调用；
- Chroma向量索引；
- 华为Rerank；
- AgentArts编排；
- 真实挂号、车位或医院内部系统接入；
- 诊断、处方和个体化治疗建议。

v2验收后，单独制定 `huawei-hospital-rag-index` 计划，使用冻结v2语料生成华为向量、建立版本化Chroma集合并运行华为Rerank；之后再制定AgentArts工具接入计划。
