# 江苏医院 V2 独立混合检索设计

日期：2026-11-13

状态：已获用户批准

范围：`data/jiangsu_hospitals_v2` 中 15 家医院、45 条已审核官方记录

## 目标

将江苏医院 V2 官方资料接入 CareGuide，形成与通用医学知识库隔离的医院事务知识库。系统针对挂号、院区、地址、联系方式、停车和就诊流程等问题，执行带医院范围约束的 BM25 与向量混合检索，并使用华为云 MaaS 重排序模型返回可追溯证据。

## 方案选择

采用独立 Chroma 集合，而不把医院资料合并进通用医学集合。

选择原因：

- 防止医院规则和疾病医学知识互相污染。
- 可以在检索前按医院、城市和院区过滤。
- 医院资料更新时可独立重建索引。
- 便于评测范围隔离和来源完整性。

未采用方案：

- 合并现有通用医学集合：实现较少，但增加跨领域误召回风险。
- 仅使用 BM25：成本最低，但对口语、简称和近义表达的召回能力不足。

## 数据边界

唯一正式输入为 `data/jiangsu_hospitals_v2` 中已通过审核清单的记录。索引不得摄入候选区、未审核开放数据或网页抓取临时文件。

每个索引文档至少保留：

- 记录 ID 与医院 ID
- 医院、城市和院区名称
- 资料类型与正文
- 官方来源 URL
- 发布或核验日期
- 审核状态
- 语料版本与指纹

索引集合名称绑定语料指纹。语料变化后不得静默复用旧集合，必须显式重建或验证后复用。

## 架构与数据流

### 建库

1. 加载并验证医院 V2 清单、医院、记录和来源文件。
2. 拒绝未审核、缺少来源或元数据不完整的记录。
3. 使用华为云 MaaS `bge-m3` 生成 1024 维向量。
4. 将正文、向量和完整元数据写入独立 Chroma 集合。
5. 保存集合绑定信息，包括语料指纹、Embedding 模型和向量维度。

### 查询

1. 从请求中解析医院、城市、院区及医院事务意图。
2. 先应用医院范围过滤，再从允许范围内生成候选。
3. BM25 与 Chroma 向量检索分别召回候选。
4. 使用 RRF 融合两路排序，候选上限为 Top-20。
5. 使用华为云 MaaS `bge-reranker-v2-m3` 重排，最终返回 Top-5。
6. 回答生成层只使用返回证据，并展示医院名称、官方来源与资料状态。

通用疾病医学问题继续使用现有通用知识库。医院规则与医学建议不得在同一无边界候选池中竞争。

## 安全与失败处理

- 缺少医院条件且问题依赖具体医院规则时，先要求用户补充医院。
- 指定医院不在当前 15 家覆盖范围时，明确说明未覆盖。
- 检索无结果时返回“当前官方资料未覆盖”，不得由模型猜测。
- 华为 Embedding 或 Rerank 服务失败时记录脱敏错误；不得输出 API Key。
- 向量服务失败不得把未经过滤的跨医院内容作为降级结果。
- 所有回答保留来源 URL，开放研究数据不得冒充医院官方规则。

## 成本控制

- 首次只向量化 45 条已审核记录。
- 语料指纹未变化时复用已验证索引，避免重复调用 Embedding。
- 先做范围过滤，再调用 Rerank；每次最多重排 20 条候选。
- 测试使用最小必要请求并记录调用量，不在自动测试中重复执行真实付费调用。

## 验收标准

1. 15 家医院和 45 条记录全部写入独立集合，数量与审核清单一致。
2. 集合元数据记录语料指纹、`bge-m3` 与 1024 维配置。
3. BM25 和向量两路候选都可在诊断信息中观察到。
4. RRF 融合候选不超过 20 条，Rerank 最终结果不超过 5 条。
5. 指定医院查询不会返回其他医院资料。
6. 离线 45 条评测保持既有基线，范围违规为 0。
7. 至少完成挂号、院区/地址、停车/行动不便三类真实华为 API 端到端测试。
8. CareGuide 对话答案包含官方来源；未覆盖问题明确拒绝猜测。
9. 全部自动化测试通过，且不会把 `.env` 或密钥写入日志、索引或版本库。

## 非目标

- 本阶段不扩展到全国医院。
- 本阶段不替换现有通用医学知识库。
- 本阶段不训练或部署自托管 Embedding/Rerank 模型。
- 本阶段不将实时停车余位包装为医院官方静态知识。
